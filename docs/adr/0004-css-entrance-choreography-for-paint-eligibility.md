# Move Engineering Notebook entrance choreography from Motion to CSS

Every Portfolio Page's entrance — page identity settling, rules drawing, records registering — is now driven by CSS animations rendered into the server HTML, not by Motion variants run after hydration. Shared primitives still own consistent reveal, focus, hover, and press behavior through common timing tokens, as ADR-0001 established; only the mechanism moved. Interaction that genuinely depends on runtime state — the mobile wayfinding disclosure, the active-route underline's shared layout animation — remains on Motion, because that work happens well after load and costs nothing on the critical path.

The prior implementation shipped every above-the-fold element from the server at `opacity: 0`, holding it invisible until the JS bundle downloaded, React hydrated, and a `pageIdentitySettled` callback chain confirmed the page title's animation had reported completion. Lighthouse traces on the production build showed First Contentful Paint and Largest Contentful Paint arriving 800–950ms after the page had already painted, entirely because the paint-eligible content stayed transparent through that gap. CSS animations keyed off a server-rendered `--notebook-delay` custom property remove the hydration dependency: the entrance starts at first paint instead of waiting for a script to run at all.

Removing the hydration dependency was necessary but not sufficient. Chrome excludes an element that is fully transparent or fully clipped at the moment it paints from both FCP and LCP, and does not reconsider it once a later frame reveals it — the reveal runs on the compositor, not as a new paint Chrome re-evaluates. An entrance where the page title and introduction both fade in from `opacity: 0` therefore reports no FCP and no LCP at all, confirmed directly against the built pages, regardless of how quickly or legibly the content actually appears on screen. The fix is a standing constraint, not a one-time adjustment: at least one paint-eligible, above-the-fold element must be opaque in the server-rendered HTML. Every Portfolio Page's introduction fills that role — `notebook-in-introduction` settles on `transform` only, never `opacity` — because it is the one piece of page identity every route composes. The page title keeps its full clip-path wipe and fade, and the section code / Greeting keep their fade, because the introduction underwrites the metrics for the page as a whole.

DOM order stands in for Motion's explicit `stagger()` sequencing: a record group names a base offset and step once as inline custom properties (`--notebook-stagger-base`, `--notebook-stagger-step`), and each child's position in the DOM resolves its own delay through `nth-child` selectors in `app/motion.css`, with no per-item prop threading and no runtime sequencing. The CV's irregular heading-then-rows-per-section sequence is the one case that does not fit DOM-order stagger; it keeps resolving absolute offsets from `notebookSectionSequenceStarts`, now rendered as inline delays rather than Motion `delayChildren`. Because the entrance carries no component state, every Notebook primitive, presentation module (Work, Read, Play), the CV, the Contact list, the footer, and the Portfolio Page shell itself now render on the server; only the Site Header, the greeting, and the top-level motion/theme providers remain client components.
